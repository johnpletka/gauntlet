## §1 Overview

### 1.1 Problem statement

Gauntlet's pitch is *adversarial multi-model review*, but each cycle runs exactly one reviewer, one pass, reading a diff. Three consequences observed across the bootstrap and the first real runs:

1. **Defect coverage is one model's blind spots.** A single reviewer profile (`codex`/`gpt-5.5`) reviews every phase. Findings it structurally misses — spec-coverage gaps, security posture, behavioral defects that only appear when the code *runs* — stay missed. The starkest instance is BOOTSTRAP-NOTES #54: a phase silently shipped 25% of its planned FRs and the diff-scoped review had no mechanism to notice, because nothing checks the diff against what the plan *promised*, and nobody executes the deliverable beyond `uv run pytest` on tests the builder itself wrote.

2. **Phase gates are all-or-nothing: a pipeline either stops for a human at every phase, or never stops at all.** *(Corrected in v0.5 — the v0.3/v0.4 text claimed "every gate parks for a human even when round 1 found zero blocking/major findings … the exact conditions under which humans rubber-stamp". Two things were wrong with that, and FR-4 was built on both.* ***(a)*** *It was false for the shipped pipeline: `standard.yaml` configures no phase gate whatsoever, so phases already proceed automatically after a converged cycle — there was no rubber-stamping to eliminate and no gate latency to recover. The rubber-stamp problem was real on `bootstrap.yaml`, which gates every phase unconditionally, and was generalised to a pipeline that does not behave that way.* ***(b)*** *"Round 1 found zero blocking/major findings" describes a state adversarial review is designed to prevent from passing silently — on this repo's own nine-phase run it never once occurred. A predicate keyed to it fires only when the reviewers underperform.)* The real problem is the absence of a middle setting: a phase whose evidence is unambiguous should flow, and a phase whose evidence is ambiguous should stop — and today's gate policy can express neither, only "always" or "never". Where every-phase gates *are* configured, their latency (meetings, overnight) dominates multi-phase wall-clock and trains inattention for the gates that matter.

3. **The pipeline learns nothing between runs.** Retro produces proposals, `gauntlet trend` aggregates stats, manifests record every finding and verdict — and none of it feeds forward. The reviewer re-discovers the same project-specific failure patterns (the judge path-boundary bugs took four rounds across runs, #29–#32); triage re-litigates finding types a human already declined with recorded reasoning; the plan-author sizes phases with no cost model, producing the oversized phases that both hide incompleteness (#54 cause 4) and blow the provider window (harness-efficiency §1.1).

4. **Convergence can close accepted-but-unfinished work silently** (issue #49, from a real adopting-repo run, `quote-source-badges`). The convergence predicate treats a `partially_resolved` confirm verdict as forcing another round only when the *finding* is blocking severity (`engine/cycle.py`: `verdict == "partially_resolved" and severity == "blocking"`); a `fix_now` partial on a major finding converges as effectively closed. Three prompt-level gaps compound it: fixers close enumerated obligations on the headline rather than the full list (the run's FR-5.1 case shipped *no-write* while silently dropping *no-read*/*no-payload*); an untestable acceptance oracle is triaged as a quality nit rather than a blocker; and artifact-mode confirms never check that a fix left the document internally consistent (the run's F-006 fix corrected the strategy section while the deliverable section still asserted the opposite). The harness-efficiency run itself demonstrated the escape live: its P1 cycle converged with `confirm_counts: {partially_resolved: 1}` surfaced-but-not-carried.

### 1.2 Solution summary

Widen detection, then use the widened evidence to narrow ceremony. (a) **Ensemble review**: an adversarial cycle accepts multiple reviewers, each with a distinct lens (correctness, spec-coverage, security), findings merged and deduplicated before triage — spending unconstrained-provider budget on diversity, the tool's founding premise. (b) **Behavioral verification**: a sandboxed verifier sub-step that *executes* the phase deliverable against the plan's acceptance criteria in a disposable worktree copy and reports observations as findings — a signal class no diff reader produces. (c) **Phase-completeness machinery** (the #54 preventions): acceptance-clause→test mapping validated deterministically at the phase gate, deferral-reference reconciliation against real phases, and a phase-size lint. (d) **Evidence-tiered gates**: a per-gate policy allowing auto-approval only when a strict clean-signal predicate holds, every auto-approval stamped with its evidence snapshot — contingent on the upstream spec check. (e) **Cross-run learning**: reviewer lens files and a declined-findings registry maintained through the existing ratified-proposal governance, and trend-derived cost/size stats injected into plan authoring. (f) **Convergence honesty** (issue #49): an accepted finding confirmed `partially_resolved` is non-converged by definition — the engine predicate says so and the confirm pass emits the concrete remainder as a carryable finding; fixers treat enumerated obligations as checklists; untestable acceptance oracles triage as blocking; artifact-mode confirms check intra-document consistency.

### 1.3 The assumption this validates

**Reviewer diversity yields materially more unique legitimate findings than a second pass by the same reviewer — enough to justify the added review cost.** This is the tool's core premise, currently asserted rather than measured. P1 instruments the ensemble so every finding carries its source and dedup fate, making yield-per-reviewer a measured quantity. If the assumption fails (near-total overlap), ensemble review is dropped and the budget shifts to behavioral verification (FR-2), which produces a *different kind* of signal rather than more of the same kind.

## §2 Goals and Non-Goals

### 2.1 Goals

| ID | Outcome | Need served |
|----|---------|-------------|
| G1 | Each review round's findings come from ≥ 2 independent lenses, with per-lens yield measured | Defect coverage beyond one model's blind spots; the multi-model premise made real and measurable |
| G2 | A phase cannot pass its gate with planned acceptance criteria that cite no existing test, or deferrals that point nowhere — the deterministic gate proves every clause maps to a real, collector-enumerated test id (citation/existence), while whether that test meaningfully exercises the clause (sufficiency) stays the review panel's job | #54 class (silent partial delivery — absence of a mapping/test) is structurally closed |
| G3 | The deliverable is executed, not just read, before a phase gate | Behavioral defects surface pre-merge |
| G4 | Human attention concentrates on gates where the evidence is ambiguous; clean-signal gates clear without a human when policy allows | Gate latency stops dominating multi-phase wall-clock; attention isn't trained into rubber-stamping |
| G5 | Every run makes the next run better: recurring findings become lenses, declined findings stop recurring, phase sizing uses measured costs | The corpus of manifests becomes an asset instead of an archive |
| G6 | An accepted (`fix_now`) finding cannot close while a material remainder is unresolved: partials force another round or park, enumerated obligations close item-by-item, and a fix cannot leave the document contradicting itself | Issue #49's silent-closure class is structurally shut |

### 2.2 Non-Goals (v1)

- **Everything in `runs/harness-efficiency/prd.md`** — resilience, context scoping, tiering, observability plumbing. Companion, not overlap.
- **Speculative phase overlap and parallel phase execution** (needs worktree isolation, already deferred in FUTURE.md; window-bound anyway).
- **Auto-tuning prompts from outcomes.** Lenses and registries change only through the existing ratified retro-proposal process — no self-modifying prompt loop.
- **CI-side review integration** (GitHub PR review bots). The PR remains the human audit boundary.
- **More than three reviewers per cycle.** v1 caps the panel; diminishing-returns measurement (§9) decides any expansion.
- **Auto-approving PRD or plan gates.** FR-4 applies to per-phase code gates only; document ratification stays human unconditionally.
- **Issue #49's secondary observation** (the retro proposal-diff generator emitting non-applying diffs). A real bug, but in the proposals machinery, not the cycle — tracked separately, not absorbed here.

### 4.2 Key design decisions

| Decision | Choice | Rationale |
|---|---|---|
| Where diversity comes from | Distinct lens prompts on distinct profiles (may be distinct providers), not N runs of one reviewer | Different models *and* different questions; same-model reruns measure noise, not coverage. Panel members run on unconstrained providers — no builder-window contention. |
| Dedup placement | Deterministic merge (same file + overlapping location per §6's normalized-location model + same category **+ compatible claim fingerprint** ⇒ mark duplicate, keep the higher-severity phrasing, record all sources) **before** triage | Triage is per-finding and priced per call; dedup first avoids paying to re-litigate the same defect N times. Deterministic rule with a fully specified overlap algorithm (§6) covering line, section, and whole-file locations, not an LLM judgment — determinism over cleverness. Claim compatibility is required *in addition* to location+category so that two unrelated findings sharing a file (e.g. a whole-file/line-less finding and a precise line-range finding making different claims) are not collapsed: only primaries reach triage (FR-1.2), so an over-merge silently drops the secondary claim. Dedup fails toward keeping findings — an un-merged duplicate is one wasted triage call; an over-merge is a lost defect. |
| Verifier's write access | Executes in a disposable copy of the worktree (or throwaway git worktree), never the run worktree; emits findings only | Preserves the reviewer read-only contract's *intent* (no mutation of the reviewed state) while allowing execution; the mutation guard keeps watching the real tree. Fail closed: verifier infra failure fails the sub-step, it does not silently skip. |
| Completeness check mechanism | Deterministic gate (mapping file ↔ collector-enumerated ids; `pytest --collect-only` is the v1 default collector, FR-3.2), not another LLM review. Enumeration is a **bounded engine subprocess in a disposable copy** with a stripped env — no LLM in the evidence path, and the gate runs both pre- and post-cycle (FR-3.2, v0.4 §B) | #54's lesson is that judgment-based review misses absence; absence is checkable mechanically. The reviewer panel's spec-coverage lens complements, not substitutes. An LLM asked to echo collector stdout can truncate (false park) or fabricate (false pass) — determinism over cleverness applies hardest to the evidence path itself. |
| Auto-approval predicate | Strict conjunction: converged in round 1 · **zero blocking/major legitimate findings left OPEN** (v0.5: open-based, not raised-based — a serious finding accepted `fix_now` and confirmed `resolved` does not block; deferred, rejected, unconfirmed, or non-`resolved` does) · acceptance gate passed · tests green · zero escalations · zero reviewer mutations · verifier ran clean · **evidence is fresh** (v0.4 §D1: a tests/acceptance record predating the cycle is a miss when the cycle landed `P<N>.x` fix commits, unless a same-type step re-proved the signal afterwards — the shipped `acceptance-recheck` does this for the acceptance signal) | Any single ambiguous signal parks for a human. Freshness is its own conjunct because a round-1-converged cycle can still land a fix commit for an accepted minor finding: evidence produced *before* that commit no longer describes the tree the phase ships, so "green" and "converged" can both be true of a tree that no longer exists. The findings conjunct is open-based because the raised-based form measured **0/9** on this repo's own run — it asked review to have found nothing, which is the one outcome an adversarial panel exists to make unlikely, and FR-1 pushes it further out of reach. "Nothing serious is still open" is the property a human at a rubber-stamp gate is actually checking; "nothing serious was ever found" is not. The predicate is evidence the pipeline already records — no new judgment call, just a policy over existing facts. Because FR-2's verifier is *optional* per code cycle, `verifier ran clean` cannot hold on a phase with no verifier: `auto_when_clean` is therefore valid only on a code phase that configures a verifier sub-step (enforced at pipeline load, FR-4.1), and a runtime verifier that is absent/skipped is recorded `verifier: not_configured` — a predicate miss that parks closed, never auto-approves. |
| Learning governance | **Lens files** change only via ratified retro proposals, and an in-pipeline agent write to them is judge-denied (§7). **Registry** splits by role (v0.4 §C5/§F): `declined.jsonl` is an engine-appended **audit ledger** — the run records its own reasoned declines automatically, per FR-5.2 — while what that ledger is allowed to *influence* is ratification-gated, since an entry is injected as precedent only under current provenance and is retired only by a ratified `supersessions.jsonl` entry. Registry injection is advisory context, never auto-dismissal | "Approved artifacts change only through their own loop and gate" applied to prompts; a declined precedent informs triage, it does not decide it. v0.3 stated this row as "registry entries change only via ratified retro proposals", which contradicted FR-5.2's own automatic-recording requirement and read as a prohibition on the audit append itself; the governed thing is *precedent*, not the *record*. Recording every decline is what makes the ledger honest — a ledger a human must approve into is a ledger that omits the declines nobody got round to ratifying — while the ratification gate sits where poisoning would actually bite: injection into a future triage prompt. |
| Partial-closure fix depth | **Both** the engine predicate (an accepted `fix_now` partial is non-converged, period) **and** the confirm-prompt remainder capture — not prompt-only | Issue #49 offers the prompt-level path as sufficient, but a prompt instruction is probabilistic; the convergence guarantee belongs in the deterministic predicate (determinism over cleverness). The prompt half is still required: the predicate can force a round, but only a *concrete carried remainder* gives that round something actionable. Oscillation is bounded: the rule touches only accepted-and-attempted findings, never re-litigates declines, and `max_rounds` still escalates to a human. |

## §5 Functional Requirements

### FR-1 — Ensemble review

- **FR-1.1** `adversarial_cycle` accepts `reviewers: [<profile>...]` (1–3; single-reviewer config unchanged and default). Each panel member receives the same review scope plus its assigned lens fragment; members run independently (concurrently where adapters allow) and each returns findings-schema output.
  *Acceptance:* unit test: a two-member panel produces two persisted per-member findings artifacts; a one-member config is byte-compatible with today's behavior.
- **FR-1.2** Findings are merged before triage: every finding carries `source` (profile) and `lens`; the deterministic dedup rule (same file, overlapping location per the normalized-location model and overlap algorithm in §6, same category, **and compatible claim fingerprint per §6**) marks duplicates, keeps the highest-severity phrasing as primary, and records all sources on it. Two findings that share file, overlapping location, and category but whose claim fingerprints diverge are **kept as distinct primaries** — both are triaged, so no distinct claim is dropped. Only primaries go to triage.
  *Acceptance:* unit tests over the §6 overlap algorithm — line-range∩line-range, section-prefix, line-vs-whole-file, and non-overlap (adjacent sections, disjoint ranges, different files) — plus a crafted overlapping-findings case whose merged artifact has the duplicate marked, sources aggregated, and triage invoked once for the pair; and a distinct-claim case where a whole-file finding and a line-scoped finding in the same file share a category but have divergent claim fingerprints — both are kept as primaries and triage is invoked for each (no drop).
- **FR-1.3** Per-member yield is recorded in step metrics: findings raised, unique-after-dedup, and post-triage legitimate counts per (profile, lens).
  **Sole-source semantics (v0.4 §E).** `unique_after_dedup` and `unique_legit` are **sole-source** counts: a primary raised by more than one member counts toward **neither** member. Ownership of the merged phrasing is a severity/tie-break artifact, not yield — crediting the owner would make two members raising an identical set both look fully productive, masking the exact near-total-overlap case §1.3's kill criterion exists to detect. A **member is a (profile, lens) pair, not a profile**: the same profile is a valid panel entry under two lenses, so sole-source is computed over member identities (`source_members`), never over `sources`, which is profile-keyed and collapses two same-profile members into one. `unique_legit_by_member` is restricted to actual panel members — verifier findings (`source: verifier`) and carried remainders (no source, engine-synthesized `legitimate` verdicts) are not panel yield, and un-filtered they mint phantom members in the very field §9's panel-shrink governance consumes.
  **§9 reading:** a zero unique-legit total across members that *did* raise findings reads as "below any threshold" — the full-overlap kill case, the answer §1.3 asked for — not as "cannot judge".
  *Acceptance:* metrics fixture test: a run's manifest answers "unique legitimate findings per panel member" without transcript access; a primary raised by two members counts toward neither; a same-profile/two-lens duplicate is shared coverage, not sole-source; verifier findings and carried remainders mint no phantom member keys.

### FR-2 — Behavioral verification

- **FR-2.1** Code cycles support an optional `verifier` sub-step between review and triage: an agent on a designated profile receives the phase's plan section (goal + acceptance clauses) and a **disposable copy** of the post-handoff worktree, executes the deliverable (run the CLI, exercise the API, probe edge inputs), and returns findings-schema output with `category: behavioral` and the executed commands as evidence.
  *Acceptance:* integration test (marked): a fixture phase with a working feature and one behavioral bug (correct-looking code, wrong runtime behavior) yields ≥ 1 behavioral finding with command evidence; the run worktree hash is unchanged after verification.
- **FR-2.2** Verifier findings join the merged panel findings and flow through the same triage/fix/confirm machinery — no parallel process.
  *Acceptance:* unit test: a behavioral finding appears in `findings.json` alongside review findings and receives a triage verdict.
- **FR-2.3** Fail closed: verifier infrastructure failure (copy creation, sandbox launch) fails the sub-step and parks the cycle; it never degrades to "skipped, proceed".
  *Acceptance:* unit test: stubbed copy failure → cycle parks with the failure in notes.
- **FR-2.4** The `behavioral` category is added to `schemas/findings.json`'s `category` enum and to every validator/consumer that enforces it (cycle merge, triage, confirm, metrics) as one **additive** migration: pre-migration findings that use only the existing categories continue to validate unchanged, and a verifier finding whose category is not accepted end-to-end fails the sub-step closed rather than being silently dropped or coerced to another category. **Ordering (phase-order prerequisite).** This migration is the **first required sub-step of P3** and completes before any verifier fixture runs or any verifier output is validated: the schema enum and *every* consumer that enforces `category` (cycle merge, triage, confirm, metrics) migrate together, and their compatibility is verified — all existing (pre-`behavioral`) review/confirm outputs still validate — *before* verifier execution is wired. This guarantees a verifier finding's `behavioral` category can never reach a consumer that has not yet migrated (which would fail validation).
  *Acceptance:* schema/compatibility test: a pre-migration findings fixture (no `behavioral` value) still validates against the migrated schema; a verifier finding with `category: behavioral` validates and survives merge → triage → confirm; a finding whose `category` is absent from the enum is rejected at validation (fail closed), not silently passed through; and a phase-order assertion that the schema+consumer migration lands (all existing review/confirm/metrics consumers validate the migrated schema) before verifier execution is wired.
- **FR-2.5** The verifier sandbox contract in §7 is enforced and tested: confinement to the disposable copy (reads *and* writes denied outside it, via the server-authoritative per-step boundary), network default-deny at the verifier boundary, credential/secret env stripping, and a wall-clock/resource limit whose expiry fails the sub-step closed. **Subprocess hook inheritance is NOT claimed** (v0.4 §A4/§7 item 6): it is unmet under the v1 hook-mediated backend and is stated there as a named residual with its compensating controls — an FR must not assert a guarantee the implementation cannot keep, which is exactly the drift v0.4 exists to correct. What *is* tested at the subprocess boundary is each compensating control.
  *Acceptance:* tests (integration where a real sandbox is required): a verifier attempt to read a credential file outside the disposable copy is denied; a network reach under default-deny fails; a stripped secret env var is absent from the verifier process environment; an over-limit execution is killed and parks the sub-step (never "skipped, proceed"); the engine parks closed when the judge does not confirm the registered boundary denies an outside-copy read, and when a real backend turn does not fire the PreToolUse hook (never runs unhooked); a ref-mutating git command from inside the copy is denied; the scratch HOME exposes no credential directory beyond the CLI's own login surface.

### FR-3 — Phase completeness (the #54 package)

- **FR-3.1** Plan phase entries gain a required `acceptance:` list (testable clauses, inherited from the PRD's FR acceptance lines). `phase_lint` fails closed on phases without one.
  *Acceptance:* existing plan fixtures updated; lint test rejects a clause-less phase.
- **FR-3.2** The implement step's completion contract includes an acceptance-mapping artifact: each clause id → ≥ 1 concrete evidence entry `{ kind, id }`, where `kind` names the collector (`pytest` is the default; other kinds — e.g. `shell`, `golden`, `integration` — are declared per project/profile) and `id` is the node id or check that collector enumerates. A new deterministic `acceptance_gate` step, per distinct collector, verifies every cited id appears in that collector's enumeration output (`pytest` ⇒ `pytest --collect-only`; another collector runs its declared side-effect-free listing command) and that every clause is mapped; any gap parks the phase with the unmapped clauses named. v1 ships the `pytest` collector; a phase whose evidence declares a collector kind not configured for the project parks closed rather than passing unchecked. **Scope of the guarantee:** the `acceptance_gate` proves *citation and existence* — every clause maps to an id the collector actually enumerates, and no clause is unmapped — not that the cited test meaningfully exercises the clause. Test sufficiency (a cited node genuinely asserts the clause, not `assert True`) is delegated to the spec-coverage review lens (§10), by design: #54's lesson is that judgment-based review misses *absence*, which is what this deterministic gate closes; sufficiency remains a review judgment. G2 is scoped accordingly.
  **Enumeration posture (v0.4 §B).** `pytest --collect-only` is *not* inert: collection imports `conftest.py` and every test module from the branch under review, so it executes branch-authored code at import time. Enumeration runs as a **bounded engine subprocess in a disposable copy** of the worktree, under the verifier's stripped-allowlist env (no secrets; no judge vars — the child is an engine subprocess, not an agent, so there is no hook to authenticate), with a wall-clock timeout and best-effort rlimits. It is **deterministic: no LLM anywhere in the evidence path.** The P5 design routed collector stdout through an agent turn asked to echo it byte-for-byte; that is rejected, because an LLM in the evidence path can both truncate a large id list (chronic false park) and fabricate ids (false pass) — either defeats the deterministic-gate premise this FR exists to provide. **Named residual:** the subprocess is not hook-gated, so import-time network egress by branch conftest code is bounded only by the stripped env, the disposable copy, and rlimits — the same subprocess-boundary residual §7 item 6 names.
  **Project-resolved command (v0.4 §B).** The enumeration command resolves per project, engine/operator-owned and never agent-authored: an explicit `collectors.<kind>.command` config wins; else a pytest-shaped `test_command` (e.g. `uv run pytest`) supplies the project's own test environment; else the engine interpreter (correct only for gauntlet's own dev layout — pytest is not a gauntlet runtime dependency, so a hard-coded engine interpreter parks every pipx/uv-tool adopter install with `No module named pytest`).
  **The gate runs twice per phase (v0.4 §B).** Once **before** the review cycle (a cheap structural park before reviewer budget is spent) and once **after** it (`acceptance-recheck`), because the pre-cycle gate's guarantee decays the moment a fix round touches a cited test: a `P<N>.x` commit can rename or remove a mapped node id, or author new deferrals, after the gate blessed the map. The post-cycle instance re-proves citation+existence for the tree the phase actually ships. `cycle-fix.md` obliges the fixer to update the map in the same fix commit when a fix renames or moves a cited test.
  *Acceptance (v0.4 additions):* a stale map (cited id renamed by a fix commit) passes the pre-cycle gate and parks at `acceptance-recheck`; a project whose `test_command` is pytest-shaped enumerates with that command, not the engine interpreter.
  *Acceptance:* unit test: a mapping omitting one clause parks with that clause in notes; a mapping citing a nonexistent pytest node id parks; a mapping citing an unconfigured collector kind parks; a complete pytest mapping passes (existence proven; sufficiency is not asserted by this gate).
- **FR-3.3** Deferral reconciliation: "Deferred to P<N>"-style references in commit bodies and mapping artifacts are validated against the plan's actual phases; a deferral to a nonexistent phase parks; open deferrals are injected into the target phase's implement prompt.
  *Acceptance:* unit test: deferral to a phantom phase parks; a valid deferral appears verbatim in the target phase's rendered prompt.
- **FR-3.4** Phase-size lint: `phase_lint` warns (configurable to park) when a phase carries more than `max_frs_per_phase` (default 3) distinct FR references — oversized phases are where partial delivery hides.
  *Acceptance:* lint test at the boundary; park mode verified.

### FR-4 — Evidence-tiered gates *(upstream check resolved — see §11 Q1)*

- **FR-4.1** Per-phase code gates accept `policy: always` (default, today's behavior) or `auto_when_clean`. The clean predicate is the strict conjunction in §4.2; if and only if it holds, the gate auto-approves with an `auto_approval` manifest record containing the full evidence snapshot (rounds, finding counts **both raised and still-open**, acceptance-gate result, verifier result, test summary) and a notification is sent.
  **Open-based findings conjunct (v0.5).** A blocking/major legitimate finding is a predicate miss unless it was triaged `action: fix_now` **and** its confirm verdict is `resolved`. `defer`/`reject`, a non-`resolved` confirm verdict (`partially_resolved`, `unresolved`, `regression_introduced`), and *no confirm verdict at all* are each a miss — an unconfirmed fix is an unproven one, and this conjunct fails closed. The evidence snapshot records raised **and** open counts: an auto-approval that reported only "blocking: 0" would be a lie by omission now that the gate can clear a phase which raised four blocking findings and resolved all four, and FR-4.2's collective ratification depends on the human seeing both.
  **Freshness interaction.** The freshness conjunct means a phase that lands any `P<N>.x` fix commit needs its tests *and* acceptance signals re-proved after the cycle. A pipeline using `auto_when_clean` must therefore position a tests step and an acceptance gate after its cycle (`tests-recheck`, `acceptance-recheck` in the shipped `standard.yaml`); a pre-cycle-only pipeline parks on every phase that fixes anything, which is nearly every phase. Any predicate miss parks for a human exactly as today. Because the predicate's `verifier ran clean` conjunct requires a verifier and FR-2's verifier is optional per code cycle, `auto_when_clean` is valid only on a code phase that configures a verifier sub-step: a phase declaring `auto_when_clean` without a configured verifier is rejected at pipeline load (as PRD/plan gates are). At runtime a verifier that did not run clean — including one that is absent or skipped, recorded as `verifier: not_configured` — is a predicate miss and parks closed rather than auto-approving.
  **Evidence freshness (v0.4 §D1)** is the eighth conjunct: a tests or acceptance record produced *before* the cycle is a predicate miss when the cycle landed `P<N>.x` fix commits, unless a same-type step re-proved that signal after the cycle. The shipped `acceptance-recheck` (FR-3.2) supplies the acceptance half; a pre-cycle **tests** record with fix commits present therefore parks.
  **Zero-findings convergence (v0.4 §D2):** a round-1 cycle that converges with zero findings persists an **explicit empty verdict set**. Without it the archetypal clean gate — the exact case `auto_when_clean` exists for — parked forever on a missing triage artifact, making FR-4 inert in precisely its intended path.
  **Notification (v0.4 §D3):** "a notification is sent" means a **pushed advisory** (`gate-auto-approved` kind) at approval time — distinct from `gauntlet status` visibility (pull) and from the FR-4.2 PR-level collective ratification (after the fact). An auto-approval the human learns about only by looking is not a notification.
  *Acceptance:* unit tests: each single predicate violation parks; the all-clean case auto-approves with the snapshot present; PRD/plan gates reject the `auto_when_clean` policy at pipeline load; a code phase declaring `auto_when_clean` with no configured verifier is rejected at pipeline load; a run whose verifier result is `not_configured` (or otherwise not clean) parks rather than auto-approving; a round-1-converged cycle with a `P<N>.x` fix commit and a pre-cycle tests record parks on the freshness conjunct; a zero-findings round-1 convergence yields an evaluable (empty) verdict set and auto-approves; an auto-approval emits the `gate-auto-approved` advisory. **v0.5:** a blocking finding accepted `fix_now` and confirmed `resolved` auto-approves (the raised-based predicate parked it); the same finding confirmed `partially_resolved`, confirmed not at all, or triaged `legitimate`+`defer` parks, naming the finding; the evidence snapshot carries raised and open counts; the shipped `standard.yaml` phase gate is exercised end-to-end, not only synthetic fixtures.
- **FR-4.2** Auto-approved gates remain human-reversible: `gauntlet rollback` to the phase boundary works unchanged, and the run's final PR lists every auto-approved gate with its evidence snapshot so the human ratifies them collectively at the audit boundary.
  *Acceptance:* PR-draft test: auto-approved gates enumerated in `PR.md` with evidence.

### FR-5 — Cross-run learning

- **FR-5.1** Review lenses live as versioned files under `prompts/lenses/`; the retro step may propose lens additions (recurring finding patterns) through the existing proposals flow; only ratified proposals change lens files.
  *Acceptance:* wiring test: lens fragment appears in the review prompt; a retro fixture produces a lens proposal artifact; nothing mutates `prompts/lenses/` without the ratification path.
- **FR-5.2** Declined-findings registry: when a human or triage declines a finding with reasoning, its fingerprint (normalized category + location kind + claim shape) and verdict are recorded together with provenance — `repo`, `prd_family` (the PRD/run family the decline was made under), `prompt_version` and `lens_version`, `schema_version`, and the recording run id. Triage context for a fingerprint-matching future finding includes the precedent (verdict, reasoning, run id) as advisory data **only when the provenance is still current**: same repo and PRD family, and the entry's recorded prompt/lens/schema versions are still the active versions — an entry is injected only when its recorded versions have not been superseded (equal the versions in force for the current run, or are otherwise marked current by the ratified version registry). A decline recorded under a superseded prompt, lens, or schema, or under a different PRD family, is *not* injected — it is retained for audit, never surfaced as precedent. Ratified retro proposals may explicitly invalidate or supersede entries. The triager may still classify an injected match legitimate.
  *Acceptance:* unit tests: a registered decline surfaces in the triage prompt for a matching finding under compatible provenance and is absent both for a non-matching fingerprint and for a fingerprint match whose entry's prompt/lens/schema version is stale or whose PRD family differs; the registry file round-trips with the provenance fields.
- **FR-5.3** Plan authoring receives measured history: per-phase cost/duration distributions by step type from `gauntlet trend` data, plus the `max_frs_per_phase` bound, injected into the plan-author input so phase sizing is grounded in observed costs (and in the window budget, where harness-efficiency FR-10 config exists).
  *Acceptance:* prompt-render test: a repo with ≥ 1 completed run produces a stats block in the plan-author prompt; an empty history renders a stated "no history" block, not silence.

### FR-6 — Convergence honesty (issue #49)

- **FR-6.1** An accepted (`fix_now`) finding whose confirm verdict is `partially_resolved` is **non-converged by definition**: the convergence predicate treats it as a forcing open regardless of the finding's severity, and the confirm pass additionally emits a `new_findings` entry naming the *specific unresolved remainder* (with `carried_from: <finding-id>`) so the next round has a concrete target. The exact entry shape, deterministic id allocation, required fields, triage-bypass semantics, and round-N+1 merge order are specified normatively in §6 (Confirm remainder carry). Remainder severity is set by what it guards: `blocking` for a privacy/security leakage boundary or a golden/parity oracle guarding a behavior-changing refactor; `major` otherwise. `max_rounds` on the shipped `plan-cycle`/`impl-cycle` rises 2 → 3 so a carried remainder has a round to land before max-rounds escalation parks for a human — the fail-closed terminus is unchanged.
  *Acceptance:* unit test: a `fix_now` finding confirmed `partially_resolved` at `major` severity forces round N+1 (today it converges — the regression fixture is issue #49's escape); prompt-content test on `cycle-confirm.md` for the remainder-capture instruction and severity rule; fixture cycle: the carried remainder appears in round N+1's review scope with `carried_from` intact; exhausting `max_rounds` with an open remainder parks (`cycle_escalation` semantics unchanged).
- **FR-6.2** Enumerated obligations close item-by-item, not on the headline. `cycle-fix.md` instructs the fixer to treat a finding that names several discrete obligations as an acceptance checklist: restate each item, map each to the specific change or assertion satisfying it, and state any deferral explicitly rather than silently dropping it. `cycle-confirm.md` mirrors the check: any uncovered enumerated item ⇒ `partially_resolved` with the uncovered items named (feeding FR-6.1's carry).
  *Acceptance:* prompt-content tests on both templates; fixture cycle with a three-obligation finding whose fix covers two: confirm returns `partially_resolved` naming the third, and the carried remainder targets exactly it.
- **FR-6.3** An untestable acceptance oracle is a blocker, not a nit. The reviewer severity rubrics (`review-document.md`, `review-code.md`) and the triage guidance (`triage.md`) state: a finding that an acceptance criterion, parity oracle, or golden test is not deterministic enough to judge a behavior-changing refactor classifies as `blocking`, unless the finding itself supplies the exact fixture matrix and expected outcomes that make it deterministic.
  *Acceptance:* prompt-content tests; a labeled entry in `prompts/triage-corpus.jsonl` encoding the rule (the PLAN F-006 case from issue #49) so triage-accuracy evaluation covers it.
- **FR-6.4** Artifact-mode confirm passes verify intra-document consistency: the fix must not introduce *or leave* a contradiction between sections of the same document (strategy vs. deliverable, requirement vs. open questions). A remaining contradiction ⇒ `partially_resolved`/`unresolved` citing both conflicting sections.
  *Acceptance:* prompt-content test; fixture: an artifact fix that corrects one section while a second section still asserts the opposite yields a non-`resolved` verdict citing both sections.

## §6 Data & Schemas (normative excerpts)

**Finding additions (findings.json):** `source: <profile>`, `lens: <lens-id>`, `duplicate_of: <finding-id> | null`, `sources: [<profile>...]` (on primaries), `source_members: [<profile>::<lens>...]` (on primaries — the panel *members* that raised the finding, as distinct from `sources`' profiles; FR-1.3's sole-source yield is computed over these, since one profile may sit on the panel under two lenses and would otherwise collapse to a single `sources` entry). All are engine/merge-annotated — never emitted by a reviewer's strict structured output — and optional on a legacy/single-reviewer artifact, which still validates.

**Dedup grouping (FR-1.2):** findings group by **complete linkage** — a finding joins a group only if it is compatible with *every* member, so each group is a clique and a finding marked `duplicate_of` a primary is always compatible with that primary. Single linkage would be wrong: both legs of the merge predicate are non-transitive (A can overlap B and B overlap C while A and C are disjoint; claim fingerprints chain the same way), so its transitive closure suppresses findings against a primary they do not match — and only primaries reach triage, so that claim is lost silently. Grouping is greedy in canonical order (panel index, then input position), which keeps the result deterministic; complete linkage can only split groups further, never merge more, so it fails toward keeping findings. `category`'s enum gains `behavioral` as an **additive** value — the schema and every validator/consumer that checks `category` (cycle merge, triage, confirm, metrics) migrate together (FR-2.4); pre-migration findings using only the existing categories still validate, and a `category` outside the enum fails validation closed rather than being coerced or dropped.

**Normalized finding location (dedup input, FR-1.2):** before dedup, every finding's location normalizes to `{ file, start, end, section }` — `file` is the repo-relative path (or the document path in artifact mode), `[start, end]` is an inclusive line range (both `null` for a whole-file or line-less finding), and `section` is the ordered heading path for document findings (e.g. `["§5", "FR-6.1"]`, else `null`). Overlap for the dedup rule is deterministic:
- **Both line-ranged, same file:** overlap iff the inclusive ranges intersect.
- **Both section-pathed, same file/document:** overlap iff one section path is a prefix of the other (`§5` overlaps `§5/FR-6.1`; `§5/FR-6.1` does **not** overlap `§5/FR-6.2`).
- **Mixed (one line-ranged, one line-less/whole-file), same file:** the line-less/whole-file finding overlaps any finding in that file (a file-scoped finding subsumes line-scoped ones).
- **Different file/document:** never overlap.
- **Invalid/unparseable location:** overlaps **nothing**, even when the file is known (v0.4 §C2 — v0.3 said "treated as whole-file for that file", which is the *merging* direction; treating an unparseable location as file-scoped would let it subsume every finding in the file on the strength of a location nobody could read). An un-deduped finding is a wasted triage call; an over-merge is a lost defect, so this fails toward keeping.
Line ranges and section paths are never compared across kinds (a section path and a bare line range in the same file do not overlap unless one side is whole-file).

**Claim compatibility (dedup guard, FR-1.2):** location overlap + same category are *necessary but not sufficient* to merge. Two findings are marked duplicate only if their claims are also compatible — their normalized claim fingerprints (the FR-5.2/Q4 fingerprint: category + location-kind + normalized claim keywords) share the claim-keyword core. When location overlaps and category matches but the claim fingerprints diverge — the case a file-scoped/line-less finding creates, since it overlaps *every* finding in its file by the mixed-location rule above — the findings are **kept as distinct primaries** and both go to triage. Rationale: only primaries reach triage (FR-1.2), so merging on location+category alone would silently drop the non-primary's distinct claim; an un-merged duplicate costs one extra triage call, an over-merge loses a defect. Dedup fails toward keeping findings.

**Acceptance mapping (`artifacts/acceptance-map.json`):**
```json
{ "phase": "P3",
  "clauses": [ { "id": "P3-A1", "text": "resume re-enters at first incomplete sub-step",
                 "evidence": [ { "kind": "pytest",
                                 "id": "tests/unit/test_cycle.py::test_resume_mid_round" } ] } ],
  "deferrals": [ { "text": "windows path handling", "to_phase": "P5" } ] }
```

**Auto-approval record (manifest):**
```json
{ "gate_id": "phase-gate", "iteration": "P3", "policy": "auto_when_clean",
  "evidence": { "rounds": 1, "blocking": 1, "major": 2,
                "blocking_major_open": 0, "blocking_major_resolved": 3,
                "escalations": 0,
                "reviewer_mutations": 0, "acceptance_gate": "pass",
                "verifier": "clean", "tests": "142 passed, 0 failed" },
  "at": "2026-07-02T18-00-00Z" }
```
`blocking`/`major` count findings **raised**; `blocking_major_open` is what the predicate turns on and must be `0` to auto-approve; `blocking_major_resolved` is the difference. The example is deliberately *not* an all-zeros phase (v0.5): the realistic auto-approval is a phase that raised three serious findings, fixed all three, and had every fix confirmed `resolved` — recording only "blocking: 0" would hide from the FR-4.2 ratifier that anything was ever found.
`verifier` takes one of `clean | findings | failed | not_configured`; only `clean` satisfies the predicate — any other value (including `not_configured`, the value recorded when a code phase using `auto_when_clean` has no verifier configured or it was skipped) is a predicate miss and parks (FR-4.1).

**Confirm remainder carry (confirm.json `new_findings` entries, FR-6.1):** each `new_findings` entry is a **complete findings-schema object** — all fields the findings schema requires (`id`, `severity`, `category`, `location`, `claim`, `evidence`; `suggested_fix` optional) — plus the added optional field `carried_from: <finding-id>` naming the `partially_resolved` accepted finding it was split from.
- **Id allocation.** Deterministic and collision-free: the remainder's `id` is derived from its parent as `<carried_from>-r<round>-c<N>` (e.g. `F-003-r2-c0` for the first remainder carried out of `F-003` at the confirm of round 2), so ids are stable across re-runs and provenance is legible from the id alone. The `-c<N>` counter is **always explicit, including `-c0`** (v0.4 §C1 — v0.3's example showed a bare `F-003-r2`): one parent can split into several remainders, and reserving the bare `-r<round>` string as never-a-final-id means a reviewer-supplied id can never collide with an engine-allocated one.
- **Required fields / severity.** `location`, `claim`, and `evidence` describe the *specific unresolved remainder*, not the whole parent finding; `severity` follows the FR-6.1 rule (`blocking` for a privacy/security leakage boundary or a golden/parity oracle guarding a behavior-changing refactor, `major` otherwise).
- **Triage status.** A carried remainder does **not** re-enter triage: its origin is an already-triaged, `fix_now`-accepted finding, so it inherits that acceptance and enters round N+1 as a pre-accepted fix obligation, never a candidate for re-litigation (this is what bounds oscillation — declines are never re-opened). Only *fresh* reviewer findings raised in round N+1 are triaged.
- **Carry validation (v0.4 §C3).** The triage bypass is a privilege, so the engine grants it only after **validating all three legs** of the claimed parentage: the `carried_from` parent exists in the round, was accepted `fix_now`, and was confirmed `partially_resolved`. Any entry failing any leg is **demoted** to an ordinary confirm regression (triaged normally) and recorded in `engine_reconciliation.demoted_carries`. Without this, a `carried_from` string asserted by a confirm agent would mint a pre-accepted, triage-exempt obligation out of nothing. Symmetrically, a round-N+1 reviewer **restating** a carried remainder's id has that restatement dropped by the engine: the pre-accepted obligation already stands and must not be re-litigated into a fresh finding.
- **Merge order.** In round N+1 the carried remainders are merged into the round's finding set *ahead of* fresh reviewer findings (stable order: carried remainders first, then new findings), and appear in that round's review scope and in the round manifest with `carried_from` intact so the audit trail links remainder → parent.

Schema change is additive to `schemas/confirm.json`/`findings.json`; a pre-migration confirm output with no `new_findings` (or entries without `carried_from`) still validates.

**Confirm-record compatibility (v0.4 §C4).** Two shapes, deliberately distinct. The **persisted** `confirm.json` `new_findings` item requires only the true pre-migration trio (`severity`, `claim`, `location`), so a legacy record validates; the **strict confirmer-output** schema — derived in code from the persisted one, as `_reviewer_output_schema` derives the reviewer's — requires the full shape natively, because pinned strict structured output demands every property be `required`. Deriving the strict shape rather than tightening the persisted one is what keeps a pre-migration artifact readable while still forcing a live confirmer to emit complete entries.

**Declined-findings registry (`<asset_root>/registry/declined.jsonl`, append-only):** provenance fields (`repo`, `prd_family`, `prompt_version`, `lens_version`, `schema_version`) gate injection per FR-5.2 — an entry surfaces as precedent only for a matching repo/PRD-family and only when its recorded prompt/lens/schema versions are still current (not superseded). Append-only for audit; invalidation/supersession is a ratified retro proposal, not an in-place edit.

**Registry supersessions (`<asset_root>/registry/supersessions.jsonl`, append-only) — v0.4 §C5.** The concrete mechanism for FR-5.2's targeted invalidation, and the line between the two registry files. `declined.jsonl` is a **pure audit ledger**: the engine appends every reasoned decline automatically, it is never proposal-editable, and an append there confers no authority by itself. `supersessions.jsonl` is the **governed** file: it sits on the proposals allowlist (guarded to append-only diffs), and a *ratified* supersession retires a fingerprint from injection. So precedent enters triage only through a path a human ratified, while the audit trail stays complete and immutable — an entry can be retired from *influence* without being erased from the *record*.
```json
{ "fingerprint": "style/docstring-format/claim:missing-docstrings",
  "verdict": "bikeshedding", "reasoning": "...",
  "repo": "gauntlet", "prd_family": "pipeline-effectiveness",
  "prompt_version": "triage@4d3722e", "lens_version": "none", "schema_version": "findings@1",
  "run_id": "run-...", "by": "human|triage", "at": "2026-07-02T12-00-00Z" }
```

## §7 Security & Privacy

- **Verifier execution is the new attack surface:** it runs code from the branch under review. Concrete sandbox contract — enforced/tested per FR-2.5. **Enforcement is hook-mediated (tool-call level), not OS-kernel-level** (v0.4 §A, absorbing the plan-ratified Q3 re-resolution to the claude-code backend): the codex `workspace-write` mechanism v0.3 assumed is unrealizable on the pinned CLI (`codex exec` fires no PreToolUse hooks, so judge-enforced read-denial is fail-open). Hook mediation is what makes items 1/2/4 enforceable *at all*; its cost is item 6, stated honestly below rather than asserted and unmet.
  1. **Confinement.** Executes in a disposable copy outside the run worktree. The mechanism is a **server-authoritative per-step boundary**: before launch the engine registers the disposable-copy root against the verifier's own step id on the run's judge (one-shot per step id; clearing requires an engine-held lease key that never enters the sandbox env). The registered boundary **wins over the pinned repo root**, and a rung-0 confinement deny covers reads, writes, Bash path tokens, and relative `..` escapes, on symlink-resolved paths. The engine **proves** enforcement on the live judge before every launch — an outside-copy read must return the deterministic confinement deny — and unproven confinement parks the sub-step. Read access outside the copy is denied, not merely read-only, because read-only outside paths still expose credential files (normative; see item 4).
  2. **Network default-deny (two layers, distinct).** The **run-wide** posture is deny to non-allowlisted hosts (github/pypi/npm are allowlisted; the builder needs them). The **verifier-boundary** posture is default-deny with **no allowlist**, enforced in the confinement rung: network-capable tools (WebFetch/WebSearch) are withheld from the verifier's `allowed_tools`, and Bash commands reaching the network are denied. A future network-permitted verifier profile (gated on a phase's acceptance clauses requiring it) is post-v1.
  3. **Credential/env stripping.** The environment is **rebuilt from an explicit allowlist**, not filtered at read: credential- and token-shaped vars (the judge's secret patterns, `*_TOKEN`, `*_KEY`, `ANTHROPIC_*`, cloud creds) are absent by construction. Only the run's judge *hook infrastructure* keys (url/token/mode, run/step ids) are re-added — the hook cannot authenticate without them.
  4. **No credential reads.** Filesystem access outside the disposable copy is denied at the tool-call surface, so no credential file outside the copy is readable *by a verifier tool call*. Below that surface, see item 6.
  5. **Resource/time bounds.** A wall-clock deadline (hard: expiry kills the process group and fails the sub-step closed) plus rlimit CPU/address-space caps applied at spawn. rlimits **are** inherited by forked children — one of the few controls that survives the item-6 boundary — but are best-effort by platform (macOS does not honor `RLIMIT_AS`); the wall-clock kill is the hard ceiling.
  6. **Subprocess boundary — the named v1 residual (NOT inheritance).** v0.3 required that subprocesses inherit the sandbox and hooks ("no escape by shelling out"). **Under the v1 backend they do not.** The PreToolUse hook sees a Bash command, not the processes it forks, and there is no OS jail; a forked grandchild is neither path-gated nor network-gated. This is a real, ratified weakening, and these are its compensating controls, all implemented: the rebuilt allowlist env (no credentials to carry), a **scratch HOME** (children cannot discover `~/.aws`, `~/.ssh`, `~/.config/gh`), inherited rlimits, a disposable-copy cwd discarded after the sub-step, the unchanged mutation guard on the real worktree, and a git **ref-mutation deny** (the copy is a `git worktree` sharing the real repo's object store, refs, and remotes, so `push`/`tag`/`branch`/`update-ref` from inside the copy would reach real state the working-tree guard cannot see). **Residual, stated plainly:** a forked child inherits `CLAUDE_CONFIG_DIR` — the claude CLI's own credential, which it must hold to run at all — and is not network-gated below the tool-call surface. Kernel-level subprocess and network isolation requires the codex `[permissions]` backend, deferred post-v1 and gated on provisioning and pinning that profile. A run needing that guarantee must not use the v1 verifier.
  Fail closed on any sandbox setup failure (FR-2.3): an absent/unhooked backend, an unproven boundary, a copy-creation or launch failure, or a wall-clock expiry parks the cycle — never "verify skipped, proceed".
- **Panel prompts contain the same artifacts today's single reviewer sees** — no new data exposure; per-member transcripts go through the existing redaction path.
- **Auto-approval cannot silently widen:** the predicate is a fixed conjunction in code, the policy is per-gate config, document gates refuse it at load, and every auto-approval is a durable manifest record surfaced in the PR. Fail-closed default is `always` (human).
- **Registry and lenses are advisory inputs under ratification governance** (v0.4 §F — previously a convention, now an *enforced* statement). An in-pipeline agent write to `prompts/lenses/*` or `registry/*.jsonl` is **judge-denied** (rule `governed-learning-assets-in-pipeline`, matched on the operation's target paths, never on file content), so a poisoned "precedent" cannot be written by an agent at all; lens files change only through the ratified proposals flow. Registry *audit* appends are a different thing and are engine-owned: see FR-5.2 and §4.2's learning-governance row for which registry writes are automatic (the `declined.jsonl` audit ledger) versus ratification-gated (injection precedence, via `supersessions.jsonl`).

| P4 | Declined-findings registry + lens plumbing under proposal governance (FR-5.1, FR-5.2) | Precedent context measurably reduces re-litigated findings without suppressing legitimate ones. |
| P5 | Trend-informed plan authoring (FR-5.3) | Measured phase-cost history changes plan-author sizing behavior (observable in emitted phase counts/scopes). |
| P6 | Evidence-tiered gates (FR-4) — last of the trust chain because P1–P3 produce the evidence signals the predicate consumes | The clean-signal predicate identifies exactly the gates humans were rubber-stamping (measured: zero post-hoc reversals of auto-approved gates). |
| P7 | Convergence honesty (FR-6): engine predicate + the four prompt changes + `max_rounds` 3 + regression fixtures from issue #49's real escapes | Forcing accepted partials to carry converges within the round budget instead of oscillating (measured on the fixtures and the next real run); the silent-closure class is reproducibly shut. |

No forward dependencies for detection breadth: P6 consumes P1–P3's signals; P1–P5 are independent of each other. P7 changes cycle *semantics* (the convergence predicate and prompts), not detection breadth, so its detection logic is independent of the other phases — but it carries one **global coupling** that the "independent, run-last" framing must not obscure: the `max_rounds` 2 → 3 bump on the shipped `plan-cycle`/`impl-cycle` changes the round budget *every* cycle runs under, including the cycles P1–P6 exercise. Two consequences are therefore explicit: (a) if P7 runs last, its acceptance includes re-running the cycle- and gate-touching regression suites from P1–P6 under `max_rounds: 3` and confirming their acceptance assumptions still hold; (b) any earlier phase whose tests depend on a 2-round budget pins that budget in-fixture rather than reading the shipped config, so the later bump cannot silently invalidate them. Alternatively the `max_rounds` change may be pulled ahead of the other cycle/gate phases; either sequencing is valid, but the coupling is not zero. Riskiest first: P1 tests the premise the rest of the review-widening spends money on.

FR-6's evidence-tiered-gates interaction is deliberate, and v0.5's open-based predicate makes it load-bearing rather than incidental: FR-4's conjunction requires zero blocking/major *legitimate* findings left **open**, and FR-6.1 is what guarantees an unfinished accepted fix stays open — a `partially_resolved` accepted finding is non-converged by definition, so it forces another round instead of being confirmed away. Convergence honesty is therefore the mechanism auto-approval rests on: FR-4 now trusts "everything serious was resolved", and FR-6.1 is what makes `resolved` mean it.

## §9 Success Metrics

Each metric names its measurement window, the manifest field or command that evaluates it, and its v1 **enforcement mode**: *report-only* (surfaced in `gauntlet trend`/retro, no state change), *proposal* (retro emits a ratifiable proposal, no auto-change), or *auto* (the engine changes state without a human). No metric silently self-tunes config; the only *auto* actions are fail-closed (tightening or disabling), never loosening.

- **Ensemble yield:** each panel member contributes ≥ 25% unique-after-dedup legitimate findings, computed per run from the FR-1.3 per-member metrics (`metrics.ensemble.unique_legit_by_member`), read with FR-1.3's **sole-source, per-member** semantics (v0.4 §E). A zero unique-legit total across members that did raise findings is **below any threshold** — the full-overlap kill case §1.3 predicted — not an unjudgeable run. Window: two consecutive comparison runs below threshold. Enforcement: **proposal** — retro emits a "shrink the panel" proposal citing the two runs; the panel changes only on ratification (§1.3 kill criterion, governed like every lens change).
- **Completeness:** a #54-replay fixture (phase shipping a plausible subset) is caught by the acceptance gate 100% deterministically (CI assertion, per run); zero silent-partial phases across subsequent real runs, verifiable from `acceptance_gate` results in the manifest. Enforcement: **auto** in the fail-closed direction only — the gate parks a phase with an unmapped clause (FR-3.2); the metric itself is report-only.
- **Behavioral signal:** ≥ 1 triage-legitimate behavioral finding per run on average, and verifier cost ≤ 10% of run cost, both read from manifest step metrics (`metrics.verifier.legit_findings`, `agent_usage`). Window: the first three verifier-enabled runs. Enforcement: **proposal** — below threshold, retro proposes reverting the verifier to opt-in; the profile config changes only on ratification.
- **Gate economics (rewritten in v0.5).** The v0.3/v0.4 target — "human gate interactions drop ≥ 40%" — was measured against a baseline that does not exist: `standard.yaml` configured **no phase gate**, so the true baseline is zero interactions and no percentage drop is definable. It is replaced by two metrics that are actually measurable on the shipped pipeline:
  - **Selectivity:** on a multi-phase run, the phase gate auto-approves the phases whose evidence is unambiguous and parks the rest, counted from `auto_approval` records vs. `phase-gate` parks. There is no target ratio — the ratio *is* the measurement, and a run where every phase parks is a signal about the phases, not a failed metric. Baseline for comparison: this PRD's own nine-phase run, where the recalibrated conjunction holds on 8/9 (P5 converged in two rounds) and the raised-based predicate held on 0/9. Enforcement: **report-only**.
  - **Correctness of the approvals:** **zero** auto-approved gates later reversed (rollback or post-merge fix traced to that phase). This is the metric that matters, because v0.5 lets a phase auto-approve after a blocking finding was found and fixed unread. Enforcement: **auto** — a single recorded reversal flips the affected gate's effective policy to `always` for the remainder of the run and writes a manifest note pending retro; re-enabling `auto_when_clean` is a ratified config change.
- **Learning:** re-litigated findings (fingerprint-matching a recorded decline, again triaged) drop ≥ 50% run-over-run, counted from registry-match metrics (`metrics.registry.rematched`); plan-author phase-size variance vs measured costs narrows, a qualitative check surfaced at plan gates. Enforcement: **report-only** for both.
- **Convergence honesty:** **zero** silent closures — every `fix_now` finding confirmed `partially_resolved` either carries a remainder into a later round, resolves, or parks at max-rounds escalation (manifest-verifiable per cycle: no converged cycle whose final round holds an accepted partial with no `carried_from` successor); issue #49's two escape fixtures (the FR-5.1 enumerated-obligation case, the F-006 intra-document contradiction) are caught 100% deterministically (CI assertion); average rounds-per-cycle rises by < 1 (from manifest metrics — the honesty tax stays affordable). Enforcement: **auto** in the fail-closed direction only — the FR-6.1 predicate forces the round; the silent-closure count is report-only.

## §10 Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Ensemble multiplies noise, drowning triage in duplicates and bikeshedding | Deterministic dedup before triage (FR-1.2); yield metrics with an explicit kill criterion (§9); panel capped at 3 |
| Verifier sandbox escape or destructive execution | Disposable copy + a server-authoritative per-step judge boundary, proven enforcing before every launch (§7); stripped env + scratch HOME + inherited rlimits + ref-mutation deny as the subprocess-boundary compensating controls; mutation guard unchanged on the real tree; fail-closed setup. **Residual accepted for v1** (§7 item 6): a forked child is not hook- or kernel-gated — it holds no credential but the CLI's own, and reaches nothing durable. Kernel-level isolation is the post-v1 codex `[permissions]` backend |
| Acceptance clauses gamed by trivial tests (`assert True` mapped to every clause) | The gate proves *existence*, not sufficiency — by design (it closes the absence class). Test sufficiency remains the review panel's job; the spec-coverage lens is prompted to sample mapped tests |
| Auto-approval predicate too loose (rubber-stamps a bad phase) | Strict conjunction, evidence snapshot (raised *and* open counts), PR-level collective ratification, one-reversal-disables rule (§9). **v0.5 raises this risk deliberately and answers it:** moving from raised-based to open-based means a phase can auto-approve after a blocking finding was found and fixed with no human reading it. What vouches for the fix is not the fixer's say-so but four independent signals that must all hold — the confirm pass says `resolved` (and FR-6.1 makes a partial non-converged, so `resolved` cannot be a partial in disguise), tests re-run green *after* the fix commit, `acceptance-recheck` re-proves the clause→test map against the shipped tree, and the verifier executed it clean. The residual is real and accepted: a fix that satisfies all four and is still wrong auto-approves. That is what the zero-reversal metric watches and what the one-reversal circuit breaker answers |
| Predicate too strict to ever fire (the v0.3/v0.4 failure) | Measure it before shipping, against real runs, not fixtures. The raised-based predicate passed every unit test and would have fired 0/9 in production; only replaying it over this repo's own nine-phase run surfaced that. Any future conjunct change re-runs that replay (§9 selectivity baseline) — a gate policy nobody has measured on real evidence is an assumption, not a policy |
| Registry suppresses a legitimate finding that resembles a declined one | Advisory-only injection; triager retains authority; precedent includes reasoning so mismatches are visible |
| Lens files drift into prompt bloat | Ratification-gated changes only; lenses are per-member fragments, not additions to every prompt |
| Forcing partials to carry makes cycles oscillate or never converge | The rule touches only accepted-and-attempted findings (declines and non-`fix_now` verdicts are untouched); the remainder must be *specific*, not a re-review; `max_rounds` (now 3) still escalates to a human as the fail-closed terminus; §9's rounds-per-cycle metric watches the tax |
| The blocking-vs-major remainder rule (FR-6.1) is gamed or misjudged by the confirm agent | The severity rule is stated in the prompt with the two blocking categories named concretely (leakage boundaries, parity oracles). A mis-set severity does **not** change convergence: per FR-6.1 an accepted `fix_now` partial forces the next round regardless of severity, so the round is forced either way. Severity affects only how the carried remainder is reported and prioritized in the gate summary — never whether it forces the round |
